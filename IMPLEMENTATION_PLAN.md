# План развития Bunker Web

## Перед продолжением

Итерации 1–3 частично реализованы в незакоммиченных изменениях рабочей директории.
Новый агент должен сначала проверить `git diff`, выполнить `npm test`, `npm run build`
и `npm --prefix client run lint`, исправить найденные регрессии, а затем продолжать с
итерации 4. Существующие пользовательские изменения и каталог `.claude/` удалять нельзя.

## Подход KISS

Текущий движок событий уже умеет выборы, вероятностные исходы, предметы, профессии,
участников, флаги и цепочки. Переписывать или существенно расширять его не нужно.

Из первоначального расширенного замысла исключаются:

- отдельный тип `passive`;
- `tone`, `arc`, `cooldown` и история событий;
- универсальный язык условий по тегам;
- сложная балансировка последовательностей;
- право LLM самостоятельно придумывать эффекты;
- отдельные инфраструктурные релизы без пользовательской функции.

Каждая итерация ниже добавляет одну законченную возможность.

## Итерация 1. Игроки, выходы и отображение выбывших

- Разделить игровой статус `active | eliminated | kicked | left` и подключение
  `connected | disconnected`.
- После голосования или кика оставлять игрока в комнате, раскрывать все характеристики
  и показывать серым.
- Кикнутый игрок остаётся зрителем без права совершать игровые действия.
- Явный выход из лобби отправляет `leave_room`, удаляет игрока и инвалидирует сессию.
- После начала игры вышедший игрок сохраняется в истории как `left`.
- Обычный обрыв связи оставляет возможность переподключения.
- Запретить одинаковые никнеймы в одной комнате без учёта регистра.
- Исправить `Переподключение...`: подпись должна зависеть только от соединения текущего клиента.
- Добавить `node:test` и интеграционные тесты join/rejoin/leave/kick/elimination.

## Итерация 2. Удобное коллективное голосование

- Каждый активный игрок получает toggle-кнопку `Предложить голосование`.
- Повторное нажатие снимает предложение; показывается прогресс `N / M`.
- При единогласии подключённых активных игроков начинается голосование.
- Боты подтверждают старт автоматически.
- Убрать модальное окно: таблица игроков остаётся видимой.
- На desktop разместить компактную sticky-панель рядом с таблицей, на мобильном —
  панель над ней.
- Выбор кандидата показывать в панели и дополнительной колонке таблицы.
- Разрешить менять свой голос до завершения тура.
- До результата показывать только количество проголосовавших; чужие варианты остаются тайными.
- Добавить такую же toggle-механику для предложения отмены голосования; отменять при единогласии.
- Администратору оставить подтверждаемые аварийные действия принудительного запуска и отмены.
- Первая ничья запускает второй тур между лидерами; повторная ничья завершает раунд без исключения.
- На сервере использовать простое состояние `idle | proposing | ballot | cancelling`.
- Покрыть старт, отмену, смену голоса, disconnect, секретность бюллетеня и второй тур тестами.

## Итерация 3. Настройки комнаты

- Добавить окно настроек администратора в лобби.
- Настройки первой версии:
  - заполнение ботами;
  - длительность месяца;
  - частота событий;
  - автоматическая или ручная вместимость бункера.
- Хранить настройки в `GameRoom`, передавать в `RoomState` и фиксировать после начала игры.
- Добавить `update_room_settings` с серверной проверкой прав и диапазонов.
- Остальным игрокам показывать выбранные настройки read-only.
- Использовать текущие значения как defaults.
- LLM-переключатель добавить позже вместе с рабочей AI-функцией, чтобы в UI не было
  преждевременной заглушки.

## Итерация 4. Исправление профессий

- Удалить случайно назначаемые варианты способностей.
- Оставить каждой профессии одну понятную способность.
- Устранить дубли, где несколько профессий фактически делают одно и то же.
- Исправить применение на самого себя: `other` всегда означает другого игрока, если
  явно не указано обратное.
- Проверять цели и параметры на сервере.
- Не создавать универсальный сложный effect-engine: добавить только несколько действительно
  необходимых атомарных эффектов.
- Неизвестный эффект считать ошибкой загрузки пака вместо тихого игнорирования.
- Возвращать единый результат способности: изменённые атрибуты, раскрытия и
  публичное/приватное сообщение.
- Добавить по одному контрактному тесту на каждую профессию.

## Итерация 5. Баланс характеристик через простой механизм тегов

- Разрешить группировать значения в `People.yaml`:
  - `social_risk: [...]`;
  - `physical_risk: [...]`;
  - `mental_risk: [...]`;
  - `survival_bonus: [...]`.
- Нормализатор автоматически добавляет группе соответствующий тег; тег не повторяется
  у каждого значения.
- Применить группировку к чертам, фобиям, телосложению и дополнительным фактам.
- Расширить количество отрицательных значений вне категории здоровья.
- Снизить чрезмерную потерю стартовых HP от болезней.
- Добавить в существующий `participants` только два простых условия: `tag` и `tag_not`.
- Событие сможет выбрать подходящего участника по тегу, но теги не будут запускать
  отдельную систему вычисления шансов.
- Использовать теги в нескольких существующих событиях: страх влияет на панику,
  конфликтная черта — на ссору, физический недостаток — на опасную работу.
- Добавить тесты нормализации тегов и выбора участников.
- Сделать небольшой seeded balance-report, не превращая его в отдельный игровой движок.

## Итерация 6. Улучшение событий без изменения движка

- Использовать существующие `choice`, `flavor`, `outcomes`, `schedule`, `flags` и `participants`.
- Переписать минимум 8 наиболее банальных событий:
  - добавить неоднозначные решения;
  - связать последствия с предметами и профессиями;
  - использовать отложенные события там, где это оправдано;
  - убрать очевидный вариант «правильно/неправильно».
- Добавить минимум 12 положительных или нейтральных flavor-событий.
- Такие события считать пассивными на уровне контента: без выбора, с автоматическим или
  обычным подтверждением через уже существующий flow.
- Добавить несколько небольших сюжетных цепочек средствами уже работающего `schedule`,
  без новой системы арок.
- Скорректировать веса событий в YAML, чтобы положительные и нейтральные события
  выпадали заметно чаще.
- Проверять ссылки, роли, предметы и цепочки существующим валидатором.
- Добавить seeded-симуляцию распределения событий и несколько тестовых полных прохождений.

## Итерация 7. Модульный LLM-режим

### Общий модуль

- Подключить официальный OpenAI Node SDK и Responses API со Structured Outputs.
- Создать небольшой интерфейс `AiProvider.generateStructured(request)` и реализацию
  `OpenAIProvider`.
- Остальной код зависит только от интерфейса, поэтому модуль позднее можно использовать
  для предметов, текстов и других функций.
- Конфигурация: `OPENAI_API_KEY` и `OPENAI_MODEL`.
- Использовать timeout 10 секунд, `store: false`, ограничение ответа и JSON Schema.
- Добавить fake-провайдер для тестов.

### Использование в событиях

- Добавить LLM-тумблер в уже существующее окно настроек.
- Показывать его только при доступном провайдере; состояние определяется через
  `/api/capabilities`.
- Перед разрешением вероятностного события передавать модели:
  - описание ситуации;
  - базовый шанс;
  - выбранные предметы;
  - выбранные профессии и уровни;
  - допустимый диапазон модификатора.
- LLM возвращает только:
  - `chance_modifier` в ограниченном диапазоне, например от `-20` до `+20`;
  - короткое объяснение пригодности выбранных ресурсов;
  - краткую заготовку результата.
- Сервер ограничивает модификатор, самостоятельно выполняет случайный бросок и применяет
  существующий YAML-исход.
- Модель не выбирает произвольные эффекты и не изменяет состояние комнаты напрямую.
- После броска LLM может сформулировать финальную короткую запись на основе уже
  определённого исхода.
- При timeout или неправильном ответе использовать модификатор `0` и штатный YAML-текст,
  не останавливая игру.
- В обычном режиме запросы к OpenAI не выполняются.
- Покрыть успешный ответ, timeout, неправильную схему, ограничение модификатора и fallback.

## Изменения интерфейсов

- `Player`: `participation_status`, `connection_status`; старый `is_active` временно
  вычисляется для совместимости.
- `RoomState.voting`:
  - `phase`;
  - `start_approvals`;
  - `cancel_approvals`;
  - `electorate_ids`;
  - `candidate_ids`;
  - `voted_player_ids`;
  - `my_vote`;
  - `round_kind`.
- Новые WebSocket-команды:
  - `leave_room`;
  - `toggle_voting_proposal`;
  - `toggle_voting_cancellation`;
  - `cast_elimination_vote`;
  - `force_start_voting`;
  - `force_cancel_voting`;
  - `update_room_settings`.
- Полная карта голосов передаётся только в итоговом сообщении.
- Значения характеристик получают необязательный `tags: string[]`.
- LLM скрыт за внутренним `AiProvider`; OpenAI SDK не используется напрямую в игровых
  обработчиках.

## Проверка качества

- Каждая итерация завершается зелёными `node --test`, client build и lint без новых
  предупреждений.
- Случайность тестируется через injected/seeded RNG.
- WebSocket-обработчики отвечают за авторизацию и передачу команды, а правила находятся
  в отдельных сервисах.
- YAML-ошибки содержат имя файла и путь проблемного поля.
- Сетевые функции проверяются минимум в двух браузерных сессиях, включая reconnect.
- Новая сложность добавляется только при наличии непосредственного пользовательского сценария.

## Допущения

- Первый цикл изменяет только пак `Fantasy`, сохраняя возможность добавления других паков.
- Комнаты и сессии остаются in-memory.
- Голосование запускается и отменяется единогласно; администратор имеет только аварийный override.
- Кикнутые и выбывшие остаются зрителями.
- LLM-режим выбирается до начала игры и не меняется в процессе.
- Без `OPENAI_API_KEY` и `OPENAI_MODEL` AI считается недоступным.
